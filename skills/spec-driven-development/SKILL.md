# Specification-driven development

Use this workflow to formalize a True Specification conversation or carry a consequential product or system change from intent to accepted implementation, within the requested scope. A specification-only request ends with specification documents and the integrated `systems.md` map. For a narrow defect with established expected behavior, use `audit-repair`; routine maintenance, cosmetic edits, and implementation already specified at the needed level do not require the full specification path.

1. Read the adopting repository's instructions, authority hierarchy, and current context. Use its existing authoritative documents and names; this package supplies a [development method](../../docs/workflows/specification_driven_development.md), not product truth.
2. Settle the True Specification conversation and decisions, then formalize accepted intent into canonical and detailed specification documents, which define their subjects under the project's acceptance process. Architecture can itself be a specification. Existing `systems.md` may be inspected for architecture, dependencies, and impacts; it must not override newly settled decisions or supply invented requirements to preserve the old map. Label accepted decisions, proposals, open questions, and evidence; escalate consequential gaps to their owner instead of filling them in. Use only the specification layers needed for the requested scope.
3. **After writing the specifications, create or revise `systems.md`.** Review the entire current specification set, including architecture specifications and those unaffected by the latest conversation. Map specifications to the required systems and to each other through responsibilities, ownership, interfaces, upstream/downstream dependencies, data/commands/events/resources/state crossing boundaries, and shared invariants. Record specification IDs/paths, versions (or unversioned status), and decision status; check coverage, overlaps, gaps, conflicts, and whole-system coherence. Preserve an existing map's path or use the project's architecture directory (default `docs/systems/systems.md`). Follow the [handoff procedure](../../docs/workflows/specification_driven_development.md#from-conversation-and-decisions-to-specifications-and-systemsmd). An individual architecture specification does not replace this integrated map. Return missing decisions to their owning specifications, then refresh the map. Review and update it whenever specifications materially change boundaries, ownership, dependencies, interfaces, or architecture, as part of completing that specification cycle. Report a review that needs no meaningful map change without mechanically bumping its version.
4. Reuse existing document owners and apply the project's documentation standard and [document versioning](../../docs/workflows/document_versioning.md) to both specifications and `systems.md`. Sequence IDs are identities, not versions: keep the ID and stable current path for `v2`, `v3`, or `v3.1`, and archive the complete old version before replacing it. When useful, load only the needed aid: [True Specification template](assets/true_specification_template.md), [Canonical Specification template](assets/canonical_specification_template.md), [systems map checklist](references/systems_map_checklist.md), [systems.md template](assets/systems_map_template.md), [detailed system template](assets/detailed_system_specification_template.md), or [increment checklist](references/increment_specification_checklist.md). Do not create every document for every task.
5. When implementation is in scope and the relevant layers are sufficiently settled, inspect implementation, tests, schemas, interfaces, and explanatory Git history. Build an implementation plan from authority and repository reality, then use the [plan and adversarial review rubric](references/implementation_plan_review.md) when complexity warrants review. Return missing product decisions to the owning specification layer.
6. For authorized implementation, use bounded units through the [agent execution loop](../../docs/workflows/agent_execution_loop.md) and [workbranch rule](../../docs/rules/multi_agent_workbranches.md). Verify actual behavior, repair narrowly, and keep the three-failure escalation boundary. Do not reinterpret product truth to simplify code.
7. Prepare [human acceptance guidance](references/human_acceptance_checklist.md) where the project reserves final acceptance to a human owner. Report agent verification and human acceptance separately.

When a downstream layer exposes an upstream error, correct the smallest authoritative unit, propagate its effects forward, and repeat affected review. Keep project-specific decisions in the adopting repository.
