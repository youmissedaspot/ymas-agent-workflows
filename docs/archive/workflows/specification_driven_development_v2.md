# Specification-driven development

Document version: v2
Previous version: [v1](specification_driven_development_v1.md)
Change summary: Formalize conversations into specifications before deriving the integrated systems.md architecture map; preserve versioned document predecessors.

Use this workflow to formalize a True Specification conversation and settled decisions, or for substantive product or system changes when important rules, boundaries, or staged scope remain unresolved. Except for the integrated `systems.md` map, these layers are roles rather than prescribed filenames. Map them to the adopting repository's governing documents, scale them to the change, and preserve its product authority. A small, well-defined implementation task need not create every layer. A specification-only request ends with the documents and integrated map; implementation remains within the requested scope.

## Specification hierarchy

| Layer | Question it owns | Boundary |
| --- | --- | --- |
| **1. True Specification** | What is the product or system meant to be for its users? State intended experience, major rules, fundamental invariants, scope, exclusions, and unresolved decisions. | Product constitution under discussion and explicit acceptance; no implementation design. |
| **2. Canonical Specification** | Which accepted product decisions are durable authority? Formalize them with unambiguous language and stable terminology; separate settled rules from open questions. | Do not invent decisions while formalizing or let conversational notes silently become authority. |
| **3. Detailed Specifications, including architecture specifications where needed** | How does each specified capability or system behave? Define relevant invariants, inputs/outputs, states, ownership, APIs and read models, edge cases, failures, concurrency, persistence, migrations, observability, security, validation, verification, and acceptance cases. Record accepted architectural decisions in a specification when appropriate. | Derive behavior and design from accepted product decisions; keep unresolved architecture explicit. |
| **4. Integrated Systems Architecture / Map (`systems.md`)** | Taking all current specifications into account, what architecture is needed, which systems satisfy which specifications, and how do those systems and specifications relate through ownership, data, control, interfaces, dependencies, integrations, and lifecycles? | One integrated map derived from the specifications. An architecture specification can supply design detail; it does not replace this map of the whole system. |
| **5. Milestone / Increment Specifications** | Which subset of already specified systems is in this increment? Reference higher authority, dependencies, entry/exit conditions, deferrals, and acceptance criteria. | Scope selection only; never redefine product or system truth. Planning labels stay in plans and history, not durable production names. |

Discussion and acceptance settle the True Specification before canonical formalization. The conversation or decision record supplies the source material. Once accepted under the project's process, specification documents are the detailed authoritative definitions of their subjects; `systems.md` integrates those definitions across the complete set. The adopting repository determines the actual approval mechanism and precedence. If authority is silent or contradictory on a consequential choice, surface it to the owner; the map and implementation plans cannot supply missing product rules.

In every layer, label the governing authority, accepted decisions, unresolved questions, proposals, recommendations, implementation evidence, and verification results when they appear. Evidence and recommendations do not become product truth without the project's acceptance process.

## From conversation and decisions to specifications and systems.md

1. **Settle the True Specification conversation and decisions.** Capture product intent, accepted rules, scope, exclusions, and unresolved questions. Use the project's acceptance process; do not turn conversation proposals into approved decisions merely by writing them down.
2. **Turn that conversation into specification documents.** Create or revise canonical and detailed specifications for the accepted decisions. Trace consequential rules to the conversation/True Specification and decision sources. Architecture can itself be a specification document when needed. Keep proposed or unresolved architecture visibly provisional. An existing `systems.md` may be inspected for existing architecture, dependencies, and impacts, but it must not override newly settled True Specification decisions. Do not invent requirements merely to preserve that map. If new specifications change the architecture, update `systems.md` afterward. Its absence does not block writing the specifications.
3. **Then create or revise `systems.md` from the specifications.** Use the project's index to inventory and review the **entire current specification set**, not just documents produced by the latest conversation. Account for every specification's place in the architecture, including unaffected ones. Record each specification's stable ID/path, document version (or note an unversioned source), status, and mapped systems. Use the [systems map checklist](../../../skills/spec-driven-development/references/systems_map_checklist.md) and [template](../../../skills/spec-driven-development/assets/systems_map_template.md). Place a new `systems.md` in the project's established architecture directory (default `docs/systems/systems.md`); preserve the path of an existing owner.
4. **Map the whole architecture and its relationships.** Identify the systems needed to satisfy the specifications, responsibilities, reads/writes, interfaces, upstream/downstream dependencies, integrations, lifecycles, and cross-system invariants. Describe data, commands, events, resources, and state crossing boundaries. Explicitly map specifications to systems and to one another: shared contracts, dependencies, constraints, and overlaps. Link to architecture specifications for design detail; `systems.md` must still integrate the whole set rather than duplicate one architecture specification or list documents without relationships.
5. **Check coverage and consistency.** Account for every current specification and trace each mapped system and relationship to its sources. Flag conflicts, unmapped requirements, unresolved ownership, and proposed architecture for the governing owner; continue independent settled work. If mapping reveals a missing decision, return it to the conversation or owning specification, then refresh the map. The map cannot silently override accepted specification rules. Do not claim the map complete while consequential coverage gaps remain.

Version both the specifications and `systems.md` using the project's standard and [document versioning](../../workflows/document_versioning.md). A new document starts at `v1`; revising the same document preserves its sequence ID and current path, writes the newer version there, and archives the complete predecessor. Record the resulting versions and archive paths in the handoff. Sequence numbers and increment labels are never document versions.

Whenever a specification materially changes system boundaries, ownership, dependencies, interfaces, or architecture, reviewing the complete specification set and updating `systems.md` is part of completing that specification cycle. For a change that leaves an existing map accurate, report the review without mechanically bumping the map's version. Check that the architecture implied by all current specifications forms a coherent whole.

## Transition to implementation

6. **Inspect repository reality.** After the relevant specification layers are sufficiently settled, inspect current architecture, implementation, tests, schemas, interfaces, and unusual behavior's relevant Git history. Compare them with authority; history and code are evidence, not product authority. Earlier exploratory inspection may inform design without silently settling requirements.
7. **Plan.** Translate the specifications into affected components, order, ownership boundaries, migrations, tests, risks, integration points, justified compatibility needs, and exclusions. If this exposes a product gap, return to its specification owner.
8. **Review adversarially when complexity warrants.** Challenge the plan for missing requirements, contradictions, authority violations, hidden coupling, incorrect ownership, failure and concurrency gaps, migrations, security, tests, naming leaks, unjustified compatibility, and divergence from intent. A reviewer may identify gaps, not invent product decisions. Use the [plan review rubric](../../../skills/spec-driven-development/references/implementation_plan_review.md).
9. **Implement and verify.** Use bounded units, the [execution loop](../../workflows/agent_execution_loop.md), and isolated workbranches. Inspect before editing, verify each meaningful unit, repair the smallest failed unit, and reassess after three failures on that unit. Never relax accepted product rules merely because implementation is difficult.
10. **Prepare human acceptance.** Agent tests, code review, logs, schemas, and API exercises provide verification evidence. Where the project reserves final product acceptance to a human owner, prepare a concise [manual checklist](../../../skills/spec-driven-development/references/human_acceptance_checklist.md) and leave sign-off to that owner unless the repository establishes another authority model.

If detailed design or planning reveals an earlier error, repair the smallest incorrect authoritative unit, propagate the correction to dependent layers, and rerun affected review. Do not rewrite unrelated settled work or force progress through a known bad assumption.
